## Як запустити середовище (Odoo 19 + PostgreSQL 15+)

### Варіант 1. Через Docker Compose

Якщо Docker запущений, виконайте в корені репозиторію:

```bash
docker compose up -d
```
Compose запускає Odoo 19 з `--dev=all`, PostgreSQL 16 і підключає `custom_addons/` до Odoo.

### Варіант 2. З вихідного коду на Windows

Встановіть Python 3.12 і PostgreSQL 15 або новішу версію. Запустіть PostgreSQL на `127.0.0.1:5432`. У `psql` під адміністратором PostgreSQL виконайте один раз:

```sql
CREATE ROLE odoo LOGIN CREATEDB;
\password odoo
```

Введіть пароль ролі, який відповідає `db_password` у `odoo.conf`. Для локальної конфігурації в репозиторії це `odoo`. Якщо PostgreSQL використовує інший порт, передайте його параметром `--db_port`.

У PowerShell, у корені репозиторію:

```powershell
git clone --depth 1 --branch 19.0 https://github.com/odoo/odoo.git odoo19
py -3.12 -m venv venv
.\venv\Scripts\python.exe -m pip install -r .\odoo19\requirements.txt pywin32
.\venv\Scripts\python.exe .\odoo19\odoo-bin -c .\odoo.conf --dev=all
```

Якщо `odoo19/` уже є, пропустіть клонування. Створюйте `venv/` на тому комп’ютері, де запускаєте проєкт.

Якщо локальну базу `library_db` уже налаштовано в каталозі `pgdata/`, двічі натисніть [start-odoo.bat](start-odoo.bat). Він запускає PostgreSQL на порту `5433` і Odoo на порту `8069`, а тоді відкриває базу в браузері. Якщо PostgreSQL встановлений в іншій папці, задайте змінну `ODOO_PG_BIN` зі шляхом до її каталогу `bin`.

### Встановлення Library Rental

1. Відкрийте `http://localhost:8069` і створіть базу `library_db` без демонстраційних даних.
2. Увімкніть режим розробника через **Settings → Activate the developer mode**.
3. Перейдіть у **Apps → Update Apps List**, підтвердьте оновлення та знайдіть **Library Rental**.
4. Натисніть **Activate**. Дочекайтеся завершення встановлення й перевірте журнал запуску. Відкрийте **List View** у списку застосунків і зробіть скріншот рядка модуля зі статусом **Installed**. У Docker журнал доступний через `docker compose logs odoo`. За запуску з вихідного коду журнал видно у PowerShell.

### 2. Що ви виправили вручну

Після критичного рев'ю коду, згенерованого AI-асистентом, було внесено такі ручні виправлення у `__manifest__.py` та файлову структуру модуля:

1. **Виправлено формат версії у `__manifest__.py` (`version`):**
   - Установлено `'19.0.1.0.0'` відповідно до формату `19.0.x.x.x` із завдання.
2. **Очищено список залежностей (`depends`):**
   - AI-асистент додав «про всяк випадок» зайві модулі `['base', 'mail', 'contacts', 'web']`.
   - Вручну видалено `mail`, `contacts` та `web`, залишено виключно `['base']`. Це відповідає вимогам завдання: на старті читачі ще не прив'язані до `res.partner`, а зайві залежності сповільнюють запуск інстансу та ініціалізацію бази даних, підтягуючи непотрібні таблиці й дані.
3. **Очищено секцію `data` від неіснуючих файлів:**
   - AI-асистент за замовчуванням прописав у `'data'` шляхи `'security/ir.model.access.csv'` та `'views/library_views.xml'`, хоча самі моделі ще не створені.
   - Вручну залишено порожній список `'data': []`, оскільки за наявності посилань на порожні або відсутні файли Odoo видає помилку під час встановлення модуля.
4. **Перевірено та явно задано ліцензію (`license`) і прапорці застосунку:**
   - Додано поле `'license': 'LGPL-3'` (щоб уникнути попередження в логах Odoo 19 про відсутність ліцензії) та встановлено `'application': True`, `'installable': True`, щоб модуль одразу відображався у основному списку застосунків (Apps) за фільтром за замовчуванням.
5. **Перевірено ланцюжок імпортів Python (`__init__.py`):**
   - У кореневому `custom_addons/library_rental/__init__.py` залишено лише `from . import models`, а у `custom_addons/library_rental/models/__init__.py` прибрано згенеровані AI закоментовані/неіснуючі імпорти `from . import book`, щоб пакет `models` коректно імпортувався як порожній Python-модуль без `ImportError`.
   - У порожні каталоги `views/` та `security/` додано файли `.gitkeep`, щоб Git зберіг порожню структуру папок у репозиторії.

## Обґрунтування вибору `depends: ['base']`

У файлі `__manifest__.py` вказано єдину залежність `'depends': ['base']`, тому що:
- Модуль `base` є обов'язковим ядром Odoo (забезпечує роботу ORM `models.Model`, базових полів, прав доступу `ir.model.access`, системних користувачів `res.users` та базового інтерфейсу).
- На етапі Практичного заняття 1 ми створюємо лише чистий каркас без бізнес-моделей. Додавання `contacts` (якщо не використовується розширення `res.partner` прямо зараз), `mail` (chatter/повідомлення) або `sale` лише збільшить час завантаження реєстру модулів і створить зайві таблиці в БД.

## Практичне заняття 2. Моделі бібліотеки та ORM

| Зв’язок | Поля | Чому так |
| --- | --- | --- |
| Книга → примірники (1:N) | `copy_ids` ↔ `book_id` | Назва, автор і ISBN описують книгу. Інвентарний номер і стан належать фізичному примірнику. |
| Примірник → видачі (1:N) | `loan_ids` ↔ `copy_id` | Видача стосується конкретного примірника. За його історією можна визначити, чи він вільний. |
| Читач → видачі (1:N) | `loan_ids` ↔ `member_id` | Читач може мати кілька видач. Його ідентифікує унікальний номер читацького квитка. |

Поле `book_id` обов’язкове й має `ondelete='restrict'`, щоб видалення книги з примірниками було заблоковано. Поля `copy_id` і `member_id` теж обов’язкові та мають `ondelete='restrict'`, щоб зберігати історію видач. У формі видачі видно назву, автора й ISBN книги та номер читацького квитка.

Відхилення від рекомендованої структури — окрема модель `library.member` із власним ім’ям і номером квитка. Це один із дозволених варіантів кроку 3. Вона не створює записів у `res.partner`, тож читачів можна вести окремо від контактів Odoo. Якщо знадобиться спільна адресна книга, інтеграцію з контактами треба буде додати. Для модуля й далі достатньо залежності `base`.

Дата видачі за замовчуванням — сьогодні, статус — `active`. Планова дата повернення обов’язкова, щоб активну видачу можна було перевірити на прострочення. Фактична дата необов’язкова. Правило «одна активна видача на примірник» описує предметну область. Автоматичне обмеження додається в практичній №3 за методичкою.

Для окремої локальної бази з демоданими можна встановити модуль і відкрити Odoo shell такими командами з кореня репозиторію. Для локального PostgreSQL на порту `5433` додайте `--db_port=5433` до обох команд.


Якщо модуль уже встановлено з практичної №1, оновіть його через **Apps → Library Rental → Upgrade**. Демодані призначені для окремої бази. У поточній версії планова дата повернення обчислюється автоматично.

```python
from odoo import fields

book = env.ref('library_rental.demo_book_forest_song')
member = env.ref('library_rental.demo_member_andrii')
today = fields.Date.context_today(env['library.loan'])

books = env['library.book'].search([('author', '=', 'Леся Українка')])
print(books.mapped('name'))

free_domain = [
    ('book_id', '=', book.id),
    ('loan_ids', 'not any', [('state', '=', 'active')]),
]
print(env['library.copy'].search_count(free_domain))
free_copy = env['library.copy'].search(free_domain, limit=1)

overdue = env['library.loan'].search([('state', '=', 'active'), ('due_date', '<', today)])
print(overdue.mapped('copy_id.inventory_number'))

loan = env['library.loan'].create({
    'copy_id': free_copy.id,
    'member_id': member.id,
})
print(loan.state)
loan.write({'state': 'returned', 'return_date': today})
print(loan.state, loan.return_date)
env.cr.rollback()
```

[Фактичний вивід Odoo shell](docs/practice-2/orm-shell.txt). Тестова видача після перевірки відкочується, тому демодані можна використати повторно.

### Ручні правки та перевірені рішення

Реалізацію та перевірку виконано за допомогою AI. Окремі ручні правки студента на цьому етапі не зафіксовані. Під час рев’ю перевірено `ondelete='restrict'` у всіх трьох зв’язках, обов’язковість полів, унікальність номера квитка та порожню дату повернення в активній видачі.

## Практичне заняття 3. Бізнес-логіка видач

- Планова дата повернення (`due_date`) дорівнює даті видачі плюс **14 календарних днів**. Odoo зберігає результат і перераховує його зі зміною `loan_date`.
- Штраф (`fine_amount`) становить **5 грн за день прострочення після фактичного повернення**. До повернення, при поверненні вчасно або раніше він дорівнює нулю. Сума зберігається й доступна через фільтр **Зі штрафом**.
- `is_overdue` обчислюється під час читання. У списку червоним виділяються активні видачі з терміном повернення раніше сьогоднішньої дати. Видача, яку потрібно повернути сьогодні, ще не прострочена.
- У формі зміна примірника показує попередження, якщо на нього є інша активна видача.

| Обмеження | Якій помилці запобігає |
| --- | --- |
| `@api.constrains('copy_id', 'state')` | Забороняє другу активну видачу одного примірника. Поточна видача виключається з пошуку за її ID. Унікальний частковий індекс PostgreSQL захищає також від одночасного збереження двома користувачами. |
| `@api.constrains('loan_date', 'due_date')` | Не дозволяє записати планове повернення на дату видачі або раніше. |
| `@api.constrains('loan_date', 'return_date')` | Не дозволяє вказати фактичне повернення раніше за видачу. Порожня дата або повернення того ж дня допустимі. |

Під час оновлення з практичної №2 Odoo перераховує збережені терміни та штрафи. Якщо в старій базі вже є дублікати активних видач або повернення раніше видачі, оновлення зупиниться та покаже ID запису для виправлення.

### AI-рев’ю

AI реалізував обчислення, попередження, обмеження та зміни форми. Під час рев’ю додано попереднє обчислення `due_date`, бо у версії №2 це вже обов’язкове поле. З демозаписів прибрано задану вручну планову дату, щоб її визначав compute-метод. Для штатного редагування попередження виключає `_origin.id`, а перевірка при збереженні — ID самого запису. Перевірено, що `fine_amount` залежить від обох дат, обидва поля для пошуку мають `store=True`, а період і ставку задано в одному місці. Окремі правки студента не зафіксовані.

## Практичне заняття 4. Безпека бібліотеки

У категорії **Бібліотека** є дві ролі. Адміністратор Odoo автоматично отримує права бібліотекаря. Внутрішній користувач без бібліотечної ролі доступу до моделей модуля не має.

| Модель | Бібліотекар | Читач |
| --- | --- | --- |
| Книги (`library.book`) | Читання, створення, зміна, видалення | Читання даних каталогу |
| Примірники (`library.copy`) | Читання, створення, зміна, видалення | Читання даних каталогу |
| Читачі (`library.member`) | Читання, створення, зміна, видалення | Доступ відсутній |
| Видачі (`library.loan`) | Читання, створення, зміна, видалення | Читання лише своїх видач |

У читача в меню **Бібліотека** є лише **Мої видачі**. Екрани керування книгами й примірниками перевіряють роль навіть за прямим посиланням. Читання даних каталогу на рівні моделей дозволяє Odoo показувати назви й інвентарні номери у власних видачах. Картки читачів захищені правами на рівні моделі.

Поле `library.member.user_id` пов’язує картку читача з обліковим записом Odoo. Воно необов’язкове, бо в бібліотеці можуть бути читачі без облікового запису. SQL-обмеження дозволяє прив’язати кожен обліковий запис тільки до однієї картки. Якщо обліковий запис видалено, картка та історія залишаються, а поле зв’язку очищається.

Правило `[('member_id.user_id', '=', user.id)]` має явно задану групу **Читач**. Бібліотекар і адміністратор бачать усі видачі. Якщо користувач має обидві групи, групове правило бібліотекаря зберігає повний доступ, а пункт **Мої видачі** все ще показує власні записи завдяки домену дії.

### Перевірка доступу

На демобазі `library_practice4_demo` увійдіть під користувачем `library-reader`, прив’язаним до демочитачки Олени Коваль. У **Мої видачі** є лише **LBR-001** і **LBR-007**. Під `library-librarian` доступні всі чотири видачі й пункти керування. Для цих демокористувачів паролі можна задати в налаштуваннях користувачів потрібної локальної бази. [Скріншот інтерфейсу під Читачем](docs/practice-4/odoo-reader-loans.png)

### AI-рев’ю

Групи й правила завантажуються з `security/library_security.xml` перед `ir.model.access.csv`. Після перевірки попередньої версії її чотири ACL збережено під тими самими XML ID та перенесено з групи внутрішніх користувачів до бібліотекарів. Під час оновлення це замінює старий доступ. Також прибрано стару групу внутрішніх користувачів із кореневого меню. У рядках читача перевірено всі прапорці, а в правилі — непорожню групу. Під час перевірки в браузері домен дії **Мої видачі** перенесено на збережене поле видачі `reader_user_id`, щоб цей фільтр працював без доступу до карток читачів.

## Практичне заняття 5. Оформлення повернення та QWeb-звіт

1. Під бібліотекарем відкрийте **Бібліотека → Видачі** й виберіть активну видачу.
2. Натисніть **Оформити повернення**. У модальному вікні вже вибрано видачу й підставлено поточний стан примірника. За потреби змініть стан і додайте коментар.
3. Натисніть **Підтвердити повернення**. Odoo проставляє сьогоднішню дату, статус **Повернено** й обраний стан примірника. Штраф перераховується автоматично. Коментар є частиною тимчасового запису майстра.
4. Відкрийте **Бібліотека → Читачі**, виберіть читача й натисніть шестерню біля його імені. У меню дій виберіть **Історія видач читача** з піктограмою принтера. Звіт містить книги, дати, статуси й штрафи для цього читача.

Модуль залежить від `web`, оскільки звіт використовує `web.external_layout`. Для друку з вихідного коду на Windows Odoo має знайти `wkhtmltopdf` 0.12.6 з виправленим Qt через `PATH` або `bin_path` у локальній конфігурації. [Документація Odoo 19](https://www.odoo.com/documentation/19.0/administration/install/source.html)

### AI-рев’ю

AI підготував `TransientModel`, модальну дію, прив’язку друку та QWeb-таблицю. Ці патерни збережено. Під час рев’ю перевірено `ensure_one()` і відхилення виклику з двома майстрами, перевірку `active_model` у `default_get()` та передачу ID з кнопки. Для поля, доступного лише для читання у формі, додано `force_save`, щоб Odoo передав підставлену видачу при збереженні. На сервері додано блокування рядка й перевірку стану перед поверненням, щоб повторне підтвердження не змінювало вже оформлену видачу.

У звіті модель дії й прив’язки — `library.member`. У шаблоні `docs` містить читачів, а таблиця перебирає `member.loan_ids`. Перевірка під бібліотекарем охоплює читача з двома видачами та друк з його форми. Окремі ручні правки студента не зафіксовані.

## Практичне заняття 6. Автоматизація та фінальна демонстрація

Завдання **Library: перевірка прострочених видач** (`ir_cron_check_overdue_loans`) зареєстроване в `data/ir_cron_data.xml`. Перший запуск заплановано на найближчу **02:00 UTC**, далі перевірка відбувається щодня від імені адміністратора Odoo з правами бібліотекаря. У журналі записуються ID видачі, інвентарний номер, планова дата повернення та підсумкові кількості знайдених, оброблених і помилкових записів. `library.loan` не використовує `mail.thread`, тому cron фіксує прострочення в журналі. У списку активні прострочені видачі позначає обчислюване поле `is_overdue`.

У свіжій демобазі **7 книг, 15 примірників, 4 читачі та 7 видач**. Є дві прострочені активні видачі, дві активні в межах терміну й три повернені. «Лісова пісня» має три примірники, тому можна показати одночасно зайнятий і вільний примірники однієї книги. Олена Коваль має дві видачі до початку демонстрації. Дати прив’язані до дня встановлення демоданих.

### Наскрізна самоперевірка

| Крок | Результат |
| --- | --- |
| Моделі та зв’язки | Перевірено кількість записів і зв’язки книги з примірниками та видачі з примірником і читачем. |
| Списки й форми | У браузері відкрито всі чотири списки та форми. Дві прострочені видачі підсвічено. |

### Сценарій показу на 5–7 хвилин

Для повторення використайте свіжу демобазу з поточною версією модуля та демоданими. Параметр `--with-demo` є в команді встановлення з практичної №2. Назву бази в команді змініть на `library_practice6_demo`.

1. **Каталог і видача (1–2 хв).** Під бібліотекарем відкрийте «Лісову пісню» й покажіть її примірники. У **Видачі → New** виберіть `LBR-002` та Олену Коваль. Покажіть автоматичний термін.
2. **Прострочення та штраф (1 хв).** Відкрийте червоний рядок `LBR-001`, оформіть повернення через майстер і покажіть розрахований штраф. У день встановлення демоданих він становить 35 грн.
3. **Звіт (1 хв).** У картці Олени Коваль натисніть шестерню та **Історія видач читача**. Покажіть кілька записів і штраф у завантаженому PDF.
4. **Cron (1 хв).** Під адміністратором увімкніть режим розробника. Відкрийте **Settings → Technical → Scheduled Actions → Library: перевірка прострочених видач → Run Manually**. У журналі покажіть `LBR-010` та підсумок виконання.
5. **Обмеження читача (1 хв).** Увійдіть як `library-reader`, відкрийте **Бібліотека → Мої видачі** й покажіть, що видно лише власні записи Олени.

### AI-рев’ю та матеріали

Cron відбирає записи через ORM `search()`. Прямих SQL-запитів у його обробнику немає. Під час рев’ю додано окрему точку збереження транзакції в кожен блок `try/except`. Тест штучно змінює один запис і спричиняє помилку. Зміна відкочується, а наступна прострочена видача потрапляє в журнал. Записи зі строком повернення сьогодні та повернені видачі виключаються.
